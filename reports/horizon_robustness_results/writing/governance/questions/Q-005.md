Question: How much headroom does the incumbent have because the targets are its own historical shares, compared with each optimised arm?
Why it changes acceptance: Every incumbent comparison needs this qualifier. Without it, a referee reads "the incumbent passes, the no-margin arms fail" as evidence that optimisation does harm.
Decisive test (read/recompute/none): anchors ho.incumbent.training_slack (if stored), ho.min_slack.*, ho.maxdev.incumbent; handoff §11 Q2 (document value handoff.q2.incumbent_headroom)
Class: E
Options, most to least conservative (or UNORDERED): n/a (Class E)
Ordering confirmed by: n/a
Conservative default: state the asymmetry qualitatively, using the arms' stored minimum slack
Card-specific decision rule (if any): none
Resolution: E. The incumbent's minimum required training slack depends on the training scenario set of the arm it is compared with, and both independent anchor computations (seq 27 and seq 36) report the same stored values. On the single history scenario [0, 243151), which NOM and TIGHT train on, it is 0, because the targets are the incumbent's own historical shares. On the HIST+ACT block scenario set it is 1117947199/71202343420, about 0.0157, which lies inside delta = 0.02 and outside the tightened 0.01. The single anchor ho.incumbent.training_slack is ambiguous, so ANCHOR_SPEC section D replaces it with ho.incumbent.training_slack.history and ho.incumbent.training_slack.hist_act. Both builders recompute these in a targeted revision. Claims state the headroom asymmetry with these two values and with the arms' stored minimum slack (ho.min_slack keys: about 0.020 for NOM and HIST_ACT, about 0.010 for TIGHT and HIST_ACT_T), qualified by handoff section 11, question 2.
